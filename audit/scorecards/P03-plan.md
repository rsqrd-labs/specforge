Shares P01's infra and P02's structural pattern (verify-checklist, wrap_untrusted_content,
Langfuse override). This scorecard focuses on what's distinct.

| # | Dimension | Score | Evidence / justification |
|---|-----------|-------|---------------------------|
| 1 | Task clarity & specificity | 5 | 25 mandatory sections, several with exact required table columns spelled out verbatim (`plan.py:42-43` Technology Stack table; `plan.py:66` FMEA table) — about as unambiguous as prose instructions get. |
| 2 | Role & context framing | 5 | `Role: You are SpecForge's software architect` (`plan.py:26`), scoped to "define HOW while preserving spec intent" — correctly distinguishes from spec.py's WHAT-only role. |
| 3 | Structure & organization | 5 | Same canonical ordering as P02. |
| 4 | Output format specification | 5 | The Technology Stack table (`plan.py:42-44`) is the single most rigorously specified output contract in the repo: exact column list, an enum for Support status with all 4 values defined, and a hard denylist of specific unacceptable choices. Directly parseable by the `tech_safety.py` zero-LLM validator (verified: `tech_safety.py` parses `## Technology Stack` markdown tables with a "Support status" column — the prompt's format and the downstream parser agree). |
| 5 | Examples & demonstrations | 4 | One RTM row example (`plan.py:99`), same single-example pattern as P02 — reasonable for a tabular format, but none of the 25 sections' other novel formats (ADR five-line block, FMEA row, Quality Attribute Matrix cell) get a worked example, leaving the model to infer shape from the prose spec alone. |
| 6 | Edge case & failure handling | 5 | Explicit "If the spec does not constrain a layer, pick a conservative Active default and mark it an assumption" (`plan.py:44`) — a concrete default-and-flag protocol rather than "handle it somehow." |
| 7 | Constraint completeness | 5 | The hard denylist (`plan.py:44`: Python ≤3.10, Node ≤18, Java ≤11, named deprecated LLM families, 18-month-stale libraries, DB EOL within 24 months) is unusually concrete for a system prompt. |
| 8 | Injection & untrusted-content safety | 5 | Same pattern as P02: `wrap_untrusted_content` + explicit ignore-injection sentence (`plan.py:86-87,101-102`). |
| 9 | Variable interpolation safety | 5 | Single dependency (`spec_content`), same wrap treatment, no bespoke interpolation logic to introduce a new failure mode. |
| 10 | Consistency with target model | 4 | Same as P02 — no per-provider tuning; unverified whether the 25-section, ~1400-word system prompt is equally well-followed by the mid-tier Gemini 3.5 Flash floor vs. Haiku/GPT-5.4-Mini on a long spec input. |
| 11 | Token & cost efficiency | 3 | `DENYLIST_LAST_REVIEWED` (`plan.py:10-18`) is a good freshness-tracking pattern, but the denylist text itself is a **static, hand-maintained list embedded in prompt prose** duplicating information that conceptually belongs with `model_catalog.py`'s single-source-of-truth policy (CLAUDE.md's stated principle for the tier ladder). A model/Python-version EOL change today requires editing prompt prose *and* bumping `DENYLIST_LAST_REVIEWED` *and* remembering the prompt-eval freshness grader will catch staleness only, not content drift — three places to keep in sync for one fact ("Python 3.10 is EOL"). |
| 12 | Determinism & robustness | 3 | Same generic non-determinism ding as P02. Additionally, the ADR block (`plan.py:60`) asks for exactly 5 lines per ADR with a specific reversal-cost heuristic ("at 10x scale") — a nuanced instruction that smaller/cheaper models (the cheap-primary tier this is judged against) are more likely to satisfy inconsistently than the mid/strong escalation tier; no in-prompt fallback if the model produces 4-line or 6-line ADRs beyond the critic's `ADRIncomplete` finding catching the case after the fact. |
| 13 | Maintainability | 4 | Versioned (`plan-v4`) and Langfuse-overridable. The freshness-review date mechanism (`plan.py:10-18`) is a genuinely good maintainability pattern other prompts with similar "living fact" content (e.g. tasks.py's SCA/dependency rules) don't have. |
| 14 | Testability & eval coverage | 5 | Uniquely well-covered: `harness/prompt_eval/graders/quality.py` has `denylist_freshness` (reads `DENYLIST_LAST_REVIEWED` directly, `quality.py:29-86`), `deprecated_api_hit_count`, `adr_completeness_pct`, `capacity_model_presence`, `stride_presence`, `slo_presence`, `fmea_presence` — essentially one grader per novel structural format this prompt introduces. This is the best eval-to-prompt-surface-area ratio in the inventory. |

**Top risk:** The technology denylist is prompt-embedded prose, not data read from `model_catalog.py`/`tech_safety_policy.json` at prompt-construction time — a real drift vector between "what the model is told is deprecated" and "what the zero-LLM `tech_safety.py` validator actually rejects" (the latter reads `tech_safety_policy.json`, a *separate* file). Two lists, two review cadences, one fact.

**Verdict:** EXEMPLARY (Dimension 11/12 nits noted; the denylist-duplication finding is worth a remediation-plan entry, not a severity escalation, since the freshness grader and the critic both backstop it).
