| 1 | Task clarity & specificity | 5 | "Rewrite only the selected text per the instruction. Return ONLY the replacement text" (`stage_manager.py:4037-4038`) is unambiguous; the focused-mode scope constraint ("keep the replacement tightly scoped... unless the instruction explicitly asks for expansion," `stage_manager.py:4038-4040`) correctly anticipates the main way a rewrite request goes wrong (silent scope creep). |

| 3 | Structure & organization | 5 | Cross-cutting rules → stage-specific boundary rules → security rules (system prompt), then document context → selected text → instruction → mode (user prompt) — clean, and correctly puts the *narrowest* scoping instruction (the stage boundary) closest to the model's actual constraint set. |
| 4 | Output format specification | 4 | "Return ONLY the replacement text, nothing else" (`stage_manager.py:4038`) is clear for the common case. No explicit instruction on preserving the selected text's exact leading/trailing whitespace or Markdown-list-item prefix (e.g., replacing text that starts mid-bullet) — `normalize_refine_replacement` (referenced at `stage_manager.py:4093,4167`) appears to be a code-side normalization layer compensating for exactly this ambiguity, which is a reasonable division of labor but means the prompt alone under-specifies the format. |
| 5 | Examples & demonstrations | 3 | No worked example of a good rewrite (before/after pair) anywhere in this prompt, despite it being the one core-family prompt most exposed to arbitrary, unpredictable user instructions (any free-text "instruction" the user types) — the highest-variance input in the family gets the least anchoring. |
| 6 | Edge case & failure handling | 4 | `_assert_refine_instruction_meaningful` (`stage_manager.py:4030-4032`, defined at `stage_manager.py:1065-1077`) rejects empty/no-op instructions **before** the model is ever called — good, cheap pre-flight validation that saves a wasted paid call. Large-selection handling (`large_selection` flag, `stage_manager.py:4024`) is computed but this audit did not trace how it changes behavior downstream within the excerpt read — worth confirming it actually alters the prompt/route rather than being informational-only in the `DiffResponse`. |
| 7 | Constraint completeness | 5 | The `_REFINE_STAGE_RULES` (`stage_manager.py:276-301`) per-stage boundary rules are excellent — they correctly re-derive each stage's cross-artifact contract (spec must stay implementation-neutral, plan/harness/tasks must preserve exact IDs/paths/names) for the *narrow* rewrite context, which is a non-trivial, well-executed piece of prompt engineering: a naive refine prompt would only need "match the surrounding style," but this one correctly re-imposes the full stage-boundary discipline on a small edit. |
| 8 | Injection & untrusted-content safety | 5 | Document context, selected text, and instruction are each individually wrapped (`stage_manager.py:4063-4069`) — the instruction itself (pure user free text, arguably the single most attacker-accessible field in the whole product) gets the full wrap treatment, correctly. |
| 9 | Variable interpolation safety | 4 | `sanitize_text_async` runs once and the result is shared between the no-op preflight check and the prompt build (`stage_manager.py:4025-4029`, explicitly commented as an efficiency fix — "previously each input was bleached twice on this path") — good, deliberate design. `_refine_document_context` (`stage_manager.py:1031`, referenced at `4057`) windows the document around the selection; this audit did not verify the windowing boundary can't split a requirement ID or a code fence awkwardly, which would be a minor context-quality issue rather than a safety one. |
| 10 | Consistency with target model | 4 | Same unverified-per-tier concern as the family. |
| 11 | Token & cost efficiency | 4 | Windowing the document context (`_refine_document_context`) rather than sending the full document is good cost discipline, appropriate given refine is a frequent, cheap-tier-routed, user-initiated operation. |
| 12 | Determinism & robustness | 4 | The generation-cache key (`build_generation_cache_key`, `stage_manager.py:4073-4090`) hashes the instruction + selection bounds + upstream content, so an identical refine request against unchanged content is a cache hit rather than a fresh (non-deterministic) call — a good practical mitigation for the generic non-determinism concern, at least for repeat requests. |
| 13 | Maintainability | 3 | Inline, hardcoded, **no version constant and no Langfuse hook** — the only interactive, high-frequency, user-facing generation prompt in the family with zero prompt-version tracking (contrast P02-P05's `STAGE_PROMPT_VERSIONS`). A quality regression introduced by editing this prompt is invisible to the same telemetry that tracks the four core stages. |
| 14 | Testability & eval coverage | 3 | No golden-corpus entry or grader targets refine-output quality (e.g., "does the replacement stay in-scope," "are stage-boundary rules honored") — the `markdown_fences_balanced` check (`stage_manager.py:4103-4106`) is a real, if narrow, structural safety net (catches one specific failure shape), but there's no quality-focused eval analogous to what exists for the four core stages. |

**Top risk:** Zero worked examples for the single highest-input-variance prompt in the family (arbitrary user instructions), combined with no version tracking — a silent quality regression here would be both more likely and harder to detect than in the core stage prompts.

**Verdict:** HIGH.
