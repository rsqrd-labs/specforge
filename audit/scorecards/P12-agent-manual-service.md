# P12 — `backend/services/pipeline/agent_manual_service.py` (CLAUDE.md / AGENTS.md build protocol)

**Not an API call site** — this module builds a Markdown file that is delivered
to the *user's own* downstream coding agent (Claude Code or Codex), via ZIP
export (`export_service.py:175`) or a direct GitHub push
(`github_export_service.py:731,1138`). It is scored here because it is,
functionally, a system-prompt-shaped artifact: it is designed to be read and
obeyed by an AI coding agent, exactly like the other prompts in this
inventory — it just isn't consumed by *this* codebase's own LLM calls.

**Top risk:** A successful injection that survives spec/plan generation and lands in the PLAN.md Technology Stack section rides, unsanitized, into a file (`CLAUDE.md`) that Claude Code and similar tools treat as authoritative project instructions in the user's own exported repository — a cross-agent trust-escalation path with no dedicated gate of its own.

**Self-adversarial review (advisor subagent was unavailable this run; performed an explicit argue-against-my-own-finding pass instead, per the audit's fallback instruction):**
*Argument for downgrading:* the attack requires an injection payload to survive an LLM that is explicitly instructed (`SECURITY_AND_PRIVACY_RULES`, P01) to ignore embedded instructions and to output only a plausible-looking Technology Stack table row (`Layer | Choice | Version | Support status | EOL date | Why not the next-best alternative`) — a fairly unnatural generation target even for a successfully-hijacked model, making realistic likelihood low.
*Argument against downgrading (the one that changed my read):* I initially cited `tech_safety.py`'s hard denylist and the critic's `BannedPhrase`/`DeprecatedAPI` checks as downstream defense-in-depth this payload would *also* have to survive. On inspection, neither actually defends against this: `tech_safety.py` pattern-matches for **deprecated technology names/versions** only (`_hard_denylist_findings`, `_choice_findings`), and the critic's finding kinds are scoped to coverage/shallowness/placeholders/deprecated-APIs/ADR completeness — none of the six kinds (`critic.py:47-54`) is "artifact contains embedded instructions." So the actual defense-in-depth here is thinner than my first pass claimed: the *only* thing standing between an injection surviving into the problem statement and it riding verbatim into `CLAUDE.md` is the generation-time authority-hierarchy instruction itself, once, with no structural or content-based backstop at the export boundary.
*Resolution:* the likelihood is genuinely low (requires successfully hijacking an instruction-following model against its explicit anti-injection framing, in a way that also produces syntactically-plausible table content) but the absence of *any* second gate — where every other cross-artifact risk in this codebase gets at least one structural or judged backstop — is real and easy to close cheaply (see remediation plan). Downgraded from SHIP-BLOCKER to **HIGH**, since I could not verify actual exploitability (no live payload constructed/tested) and the bar for SHIP-BLOCKER should be reserved for certain, mechanically-triggerable defects (see P14, which meets that bar with no adversarial input required at all).

**Corroborating discovery (Phase 3):** `backend/services/integrations/agents_md_builder.py` (P21) — the **generic**, non-Demo-Day `AGENTS.md` builder that runs for every GitHub-exported workspace — solves this exact risk class correctly: its `_excerpt()` helper calls `sanitize_text()` on every stage excerpt before folding it into the agent-context file, with the module docstring stating the security rationale explicitly ("the stage-derived content folded into the managed block is sanitised with the same policy as public share / PDF," `agents_md_builder.py:23-25`). This raises confidence in the finding rather than lowering it: the team has already identified and fixed this exact hazard for one downstream-agent-file generator, but the fix was not carried over to this module (P12) — a one-line reuse (call `sanitize_text` on the extracted Technology Stack body before interpolating it) closes the gap using a pattern that already exists and is already tested in the same codebase. For a `claude_code`-targeted Demo Day workspace, both files are written into the same exported repo side by side (`github_export_service.py:1137-1153`) — the sanitized `AGENTS.md` and the unsanitized `CLAUDE.md` — so the inconsistency is not hypothetical, it is two files sitting next to each other in the same delivered output with different trust treatment of the same upstream content.

**Verdict:** HIGH (downgraded from an initial SHIP-BLOCKER read after self-adversarial review; still the single highest-blast-radius gap in the inventory and worth prioritizing — see remediation plan).
