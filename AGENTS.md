# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## What This Project Is

SpecForge is a full-stack SaaS web app that turns a user's idea into a structured engineering spec through a four-stage LLM pipeline: **Spec → Plan → Harness → Tasks**. Each stage can be streamed, refined, diffed, and version-controlled. Users authenticate with Google OAuth, consume credits per generation, and can connect their own LLM API keys.

## Development Commands

### Starting the full stack (recommended)
```bash
docker compose up --build
```
- PostgreSQL on 5432, Redis on 6379, FastAPI on 8000, Vite on 5173
- The `worker` service (arq) also starts — it drains the GitHub job queue (Phase 21). Webhooks need public ingress in dev: forward `smee.io` / `gh webhook forward` → local `POST /integrations/github/webhook`, and register a **separate dev GitHub App** (its own id/key/webhook secret).

cd backend

## Architecture

### Backend (`backend/`)
FastAPI app with async SQLAlchemy (PostgreSQL) and Redis.

- **`routers/`** — HTTP endpoints grouped by domain: `auth`, `workspaces`, `stages`, `credits`, `providers`
- **`services/pipeline/`** — Core stage generation logic: runs the four-stage flow, handles SSE streaming, diffs, version snapshots, and recovery
- **`services/llm/`** — Provider adapters (Anthropic, OpenAI, Google Gemini) behind a unified gateway; routes calls based on user's configured provider
- **`services/evals/`** — Online quality scoring of generated stages
- **`services/security/`** — CSRF enforcement, prompt injection guard, output validator (detects system-prompt leakage), sanitizer (bleach), Fernet-encrypted key vault
- **`services/credit_service.py`** — Ledger-based credit accounting; checks balance before generation, charges on completion
- **`middleware/`** — Rate limiting, CSRF enforcement, auth extraction
- **`models/`** — SQLAlchemy ORM: `User`, `Workspace`, `Stage`, `StageVersion`, `CreditLedger`, `EvalResult`

### Frontend (`frontend/src/`)
React 18 + TypeScript SPA. State via Zustand; routing via React Router 6.

- **`pages/`** — `Landing`, `AuthCallback`, `Dashboard`, `Workspace` (main editor view)
- **`components/workspace/`** — The core product UI: `StageEditor`, `StageNavigator`, `DiffViewer`, `HumanReviewGate`, `StreamingOverlay`, `QualityBadge`, `CoveragePanel`, `TaskValidationPanel`
- **`services/api.ts`** — Axios client; automatically attaches CSRF token to mutating requests
- **`services/sseService.ts`** — SSE client for streaming stage generation progress
- **`store/`** — Zustand stores: `userStore`, `workspaceStore`, `stageStore`

### Key Cross-Cutting Concerns

**Auth flow**: Google OAuth → frontend `/auth/callback` → frontend calls backend `/auth/callback` → JWT access token (in-memory on frontend) + refresh token (HTTP-only cookie). CSRF tokens required on all mutating requests.

**Stage generation flow**: Frontend calls POST to trigger generation → backend streams progress via SSE → frontend `StreamingOverlay` updates in real time → `HumanReviewGate` blocks progression until user approves. Generation health is supervised by a **stream watchdog**, not a flat per-stream timeout: a stream is killed only when no provider stream **event** arrives within `LLM_STREAM_IDLE_TIMEOUT_SECONDS` (default 180) or the absolute `LLM_STREAM_HARD_CAP_SECONDS` bound (default 900) is hit. Liveness is measured on events, not visible tokens: adapters yield empty-string sentinels for reasoning/thinking deltas, pings, and usage chunks (the watchdog swallows them), so a frontier model reasoning silently for minutes is never killed while its connection is alive, and a steadily streaming generation is never killed regardless of input/artifact length (issue #19). The whole post-preflight pipeline (artifact streaming, quality gates, critic review/regenerate, persistence) runs as a background task supervised by an event pump in `StageManager.generate()`, which emits `{"progress": …}` SSE heartbeats whenever the pipeline is silent ~10s, so proxies keep the connection open end-to-end and `StreamingOverlay` shows live elapsed time instead of a frozen loading screen. Core generation (the four streamed stages and full regenerate) routes to each provider's **cheapest viable current-generation model** (Codex Haiku 4.5 / GPT-5.4 Mini / Gemini 3.5 Flash), keeping per-generation cost and latency down. The per-provider tier policy is `CORE_GENERATION_TIER_POLICY` (`stage_manager.py`), now **derived** (`core_generation_tier_policy()` → `(ladder[0], ladder[1])`) from the single declarative `CORE_GENERATION_TIER_LADDER` in `model_catalog.py` — the catalog source of truth for the per-provider cheap-tier floor (issue #26 Phase 5b; `validate_core_generation_ladder()` CI-enforces it, and a pinned test asserts the derivation is byte-identical to the pre-5b dict, so no route changed). A runtime timeout/provider failure is retried exactly once on the provider's **mid tier** — the previous fast/cheap default, Codex Sonnet 4.6 / GPT-5.4 (`pipeline_generation_fallbacks_total`) — before surfacing. Google stays mid-first on Flash (Flash-Lite is deliberately not a core-gen default, so its floor is mid; no active strong/escalation model) and surfaces failures directly. Tier-ladder/catalog hygiene policy (quarterly + on-release review, deprecate-don't-delete, one-place swap) is in `docs/evals/CATALOG_HYGIENE.md`; any change to which model actually runs rides the Phase-5 golden-corpus gate. **Cheap-primary is product-wide (issue #17 follow-up):** the `(primary, escalation)` policy has one source of truth in `services/llm/tier_policy.py` (`generation_tier_policy`, which `stage_manager._core_generation_tier_policy` now delegates to), and **every** artifact-generation feature reads it — the four core stages, full regenerate, the harness gap-patch, the **Storyboard keynote** (`storyboard_service.py` always routes through it now: cheap primary → mid escalation on a quality-gate failure, incl. truncation; Google floors at mid/Flash with no further escalation and surfaces directly; counter `specforge_storyboard_escalations_total`), and **increment generation** (`increment_service.py`, no longer pinned to mid). **Two flags gate the adaptive layer (issue #26 Phase 5.2/5.3):** `core_cheap_primary` (default **true**) wraps the live cheap-primary behavior — flip it false to revert **all** of those features (core stages, full regenerate, harness gap-patch, storyboard, increment) to the **mid-first** default (mid → strong) in one toggle; `core_complexity_routing` (default **false**) enables the deterministic, no-LLM complexity classifier (`services/llm/complexity_classifier.py`) that *raises* the starting tier (a floor, never a ceiling) for predictably hard requests — regulated/high-stakes domains, large upstream chains, prior quality-gate failures, harness/tasks stage floor — via `_apply_complexity_floor` in `stage_manager.py` (counter `pipeline_complexity_tier_floors_total`). It ships off and is enabled only after the manual live golden-corpus gate (`docs/evals/ROUTE_PROMOTION.md`); the expanded corpus (`asdd_route_golden.json`, simple/high/critical bands) and `scripts/run_llm_route_eval.py` assert the classifier deterministically, but the cheap-vs-mid **quality** comparison is the manual live step (the dry-run output is tier-identical). (Haiku 4.5 and GPT-5.4 Mini carry the full core-gen output budget because their catalog output ceilings were raised to 32768.) Output budgets live in `services/llm/output_budget.py` (`resolve_output_budget`): per-operation, clamped to the model catalog's per-model output ceiling, sized with headroom for reasoning tokens; a `provider_stopped_by_limit` repair retries once with a doubled budget. **Right-sizing is evidence-gated (issue #26 Phase 4):** budgets can be tightened per **(operation, provider)** via `OUTPUT_TOKEN_BUDGET_OVERRIDES` (ships **empty** — defaults unchanged), and only after `scripts/analyze_output_budgets.py` reads the `llm_cost_events` ledger (`output_token_percentiles`) and the pure `recommend_output_budget` gate clears for that pair — ≥200 samples, ~zero `stopped_by_limit` rate, and `ceil(p95 × 1.30)` (reasoning tokens already inside p95, never re-added) sitting below both the current budget and a completeness floor. The doubling repair stays the runtime backstop. See `docs/evals/OUTPUT_BUDGET_TUNING.md`. Chunked generation always runs every chunk — there is deliberately no early return when chunk one looks complete.

**Quality gate (Phase 19, T-247/T-248)**: After a stage streams and passes output validation but before persistence/caching, two gates run in order. First the zero-LLM `services/pipeline/artifact_validator.py` (`validate_sections`) asserts every required section heading is present (`SECTION_CONTRACTS` per stage; the Frontend Architecture section is conditional on a UI sentinel in the upstream deps) — a miss is terminal (no regenerate), raises `MissingSectionError`, and increments `pipeline_validator_failures_total`. Then `services/pipeline/critic.py` runs a cheap judge-model second pass (`critic_review`) enforcing the "Before returning, verify" invariants. **The critic is advisory, not blocking (issue #34), and now runs OFF the critical path (`critic_async_advisory`, default true — `docs/CRITIC_ASYNC_ADVISORY_PLAN.md`):** the usable draft is delivered the instant the deterministic gates pass and `done` fires; the judge then runs in a **detached background task** (`_schedule_critic_review`/`_dispatch_critic_review`, mirroring the post-`done` eval score — its own short-lived `AsyncSessionLocal`, held in `_BACKGROUND_CRITIC_TASKS`, never the pipeline task, so it survives client disconnect). On a failing verdict it attaches its findings to the already-delivered draft as non-blocking suggestions (`quality_gate_status="advisory"`, `kind="critic_findings"`, `_mark_quality_gate_advisory`, cost outcome `critic_advisory`, counted by `pipeline_critic_advisory_findings_total`) under a version staleness guard (skip if `current_version` moved), **merging** with any notice already attached at persist (the Phase-D condensed-statement notice). There is **no auto-regenerate** in this path. The frontend surfaces them via `AdvisoryFindingsPanel` from the persisted `Stage.quality_gate`, picked up by a short bounded post-`done` poll in `useStream.ts` (the single refetch is now too early). **Flip `critic_async_advisory=false`** to revert to the legacy inline path verbatim: the judge runs synchronously between the streamed draft and `done`, a failing verdict triggers exactly one platform-funded regenerate with the findings injected (counted by `BILLING_CREDITS_CRITIC_REGEN`, possibly escalated to the mid tier), and only the findings remaining after that one regenerate become advisory. The remaining *blocking* gates are the zero-LLM `missing_sections` plus the depth/`incomplete_output` and `technology_safety` checks below. **Every blocking gate kind is now overridable** (`NON_OVERRIDABLE_GATE_KINDS` is empty; `override_quality_gate` accepts all kinds; `finalise` blocks only on `quality_gate_status=="blocked"` and skips the tech-safety re-check once a version is overridden) — the user owns the artifact and can finalise it as-is. **Refunds are minimal:** only `incomplete_output` (genuinely truncated output) refunds; `technology_safety`, `missing_sections`, and the advisory critic do not (the artifact is delivered/overridable). A blocking gate resets the stage to draft and emits a `quality_gate_failed` SSE event (`kind: "missing_sections"`, `"incomplete_output"`, or `"technology_safety"`) rendered by `StreamingOverlay` with Regenerate + Override actions. The validator is the cheaper gate so it runs first. Depth is enforced mechanically before either gate by `validate_artifact_completeness` (inside the generation/repair loop): per-section minimum substantive body lengths (`_min_body_chars`: spec 120 / plan 150 / harness 60 / tasks 50 normalised chars), spec identifier floors (≥5 distinct FR, ≥3 NFR, ≥3 AC — `insufficient_requirement_ids`), and a ≥6 task-block floor (`insufficient_task_count`); the critic additionally grades proportional depth via the `ShallowSection` finding kind. The critic is fail-open (judge errors never brick a generation), its result schema cannot carry artifact bytes, and its prompt is held in code (never Langfuse). Workspace owners can bypass **both** gates with the `disable_critic` flag (`PATCH /workspaces/{id}/critic`), which writes a structured `critic_disabled` audit log row. Audit events in this codebase are structlog rows, not a DB table.

**LLM routing**: Every generation goes through `services/llm/gateway.py`. If the user has stored a provider API key (encrypted in DB), it uses that; otherwise falls back to the platform key. Credit accounting is provider-aware.

**Observability**: Prometheus at `/metrics`, structured logging via `structlog`, optional Sentry (scrubs secrets), optional OTLP. Health check at `/health` reports db/redis status.

**Generation admission control & 429-aware backoff (Scalability audit P0)**: The core **generate/regenerate** path is admission-gated (`services/pipeline/admission.py`): after the generation-cache miss and before any provider call, a generation acquires a slot across a per-process limiter (`max_concurrent_generations_per_process`), a self-healing per-user Redis lease (`max_concurrent_generations_per_user`), and a global per-provider budget (`provider_max_inflight_generations` / `_per_minute`, **shipping at 0/unlimited** until the per-org limits are measured — audit §F2/§6). Over budget fast-fails with `Retry-After`; Redis budgets **fail open**. The provider budget is a **core-generation budget** — storyboard/increment/harness gap-patch hit the same key but are governed by their own rate tiers and are not counted. There's also an HTTP-native generation rate tier in `RateLimitMiddleware` (true 429 at the edge; admission rejections inside the SSE stream surface as the existing `rate_limit_exceeded` event). A provider **429/529/503** is wrapped as `ProviderRateLimitError` (`services/llm/base.py`) and retried **in place on the same tier** (honor `Retry-After` → backoff+jitter, bounded) and **never escalated** — escalating amplifies load against an already-throttled org (audit §F2.3); the circuit breaker excludes rate-limits so a 429 can't open it and then hard-fail its own retry. Full ops + sizing in `docs/RUNBOOK.md` §14; the plan is `docs/SCALABILITY_AUDIT.md`. F8/F9 also bound the shared Redis pool (`database.build_redis_client`) and add postgres fast-fail/server guards (`db_pool_timeout`, `db_statement_timeout_ms`, `db_idle_in_transaction_timeout_ms`).

**Horizontal scale-out (Scalability audit P1)**: Four levers make the fleet scale to N instances without exhausting Postgres `max_connections` (ops in `docs/RUNBOOK.md` §15/§16). **F3** — a transaction-pooler (PgBouncer) drops in front of Postgres; the app is made transaction-mode-safe by `DB_TRANSACTION_POOLER_MODE` (default off ⇒ byte-identical), which disables SQLAlchemy's **and** asyncpg's prepared-statement caches and assigns unique statement names (`database._engine_connect_args`), validated end-to-end against a real PgBouncer (`deploy/pgbouncer/`, compose `pgbouncer` profile). In pooler mode the F9 `statement_timeout`/idle guards are stripped (startup params) — set them at the Postgres ROLE level. SQLAlchemy **pool metrics** (`specforge_db_pool_total_open`/`_checked_out`/`_overflow`/`_max`) are exported for the capacity gate. **F4** — API worker count is `WEB_CONCURRENCY`-driven via `backend/gunicorn.conf.py` (default 2; raise only after the pooler is in front; **no** `max_requests` recycling — it would sever in-flight SSE streams). **F5** — the single arq worker queue is **split** by latency class, each drained by a **separate process**: a **bulk** lane (`arq worker.WorkerSettings`, the default `arq:queue` — GitHub bulk I/O + LLM eval batches) and a **fast** lane (`arq worker.FastWorkerSettings`, `arq:queue:fast` — `billing_process_webhook` + `pr_check` + billing crons), so a bulk-export storm can't starve paid credit grants. Routing is single-sourced in `services.queue.queue_for_job` (every `enqueue()` call site unchanged); both lanes scale to N replicas (arq dedups crons per-queue) and **each global cron sits on exactly one lane**; per-queue depth + oldest-job-age are sampled by a per-worker cron (`worker.sample_queue_stats` → `specforge_worker_queue_depth`/`_oldest_age_seconds`). **DEPLOY INVARIANT: the fast worker (`worker-fast` / Procfile `worker_fast`) must run in every environment**, or paid grants never drain (backstop alerts: fast-queue oldest-age + `BillingWebhookPendingAge`). The per-installation governor (F5 #4 / T-274) already exists. **F6** — the four module-level detached-task sets are unified into one bounded `BoundedTaskRegistry` (`services/pipeline/background_tasks.py`; strong-ref-until-done preserved, `len()` → `specforge_background_tasks{registry}` gauge, high-water warning, never drops a task); the advisory eval/critic/verifier work shares a concurrency semaphore (`max_concurrent_advisory_tasks`, default 12; 0 disables) so post-`done` work can't starve live streams, while the detached generation pipeline stays ungated (bounded upstream by F1 admission).

**Tail latency & polish (Scalability audit P2)**: Ops in `docs/RUNBOOK.md` §17. **F7** — sync, GIL-holding passes over LLM-scale payloads (bleach sanitise, the full-document regex validators, the problem-statement gate, the Demo-Day construction linter, difflib in refine) no longer run inline on the event loop: they route through the single seam `services/cpu_offload.py::run_cpu_bound`, a **dedicated bounded thread pool** (`CPU_OFFLOAD_MAX_WORKERS`, default 4 — isolated from the PDF/Langfuse pools) with a **size gate** (`CPU_OFFLOAD_MIN_CHARS`, default 4096: smaller inputs stay inline because the dispatch round-trip costs more than the pass; huge ⇒ offload off, 0 ⇒ always offload). Every `*_async` wrapper (`sanitize_text_async`, `validate_async`, `scan_async`, `validate_sections_async`, `validate_artifact_completeness_async`, `compute_diff_async`, `assert_valid_problem_statement_async`, `compute_verdict_async`) is byte-identical to its sync form and propagates exceptions unchanged; bounded-small inputs (clarifier/increment/idea schema caps) and arq-worker-side paths are deliberately inline. Loop health is observable via `specforge_event_loop_lag_seconds` (per-process sampler; alert on sustained p99 > 250ms). The unauthenticated `GET /public/{slug}` read is fronted by a short **Redis payload cache** (`PUBLIC_SHARE_CACHE_TTL_SECONDS`, default 60s = the advertised `Cache-Control` max-age; positives only — 404s never cached; evicted immediately on enable/disable/rotate; fails open to the DB). Migration `0031` adds the **partial index** `ix_stages_in_progress_updated_at` matching the recovery sweep's exact predicate (additive; Postgres-only). The **PDF render pool** size is env-driven (`PDF_EXPORT_MAX_WORKERS`, default 2, clamped ≥ 1).

**Starter templates (Phase 14)**: The `templates` table is populated automatically on every container start by `backend/scripts/seed_templates.py`, invoked from `backend/entrypoint.sh` after `alembic upgrade head` and before uvicorn. The seed is idempotent (Postgres `INSERT ... ON CONFLICT (slug) DO UPDATE`) and exits 0 against an already-populated DB. To add a new starter, edit `STARTER_TEMPLATES` in the seed script — never rename a slug in place; instead add a new slug and mark the old one `active=False`.

**Public share route (Phase 14)**: `/p/:slug` is a top-level unauthenticated React route (registered outside the auth guard in `App.tsx`, lazy-loaded). It reads from the unauthenticated `GET /public/{slug}` backend endpoint via a bare axios call — no CSRF, no auth headers. Both surfaces inject `noindex, nofollow` (frontend `<meta>`, backend `X-Robots-Tag`). The route prefix `/p/` is also disallowed in `frontend/public/robots.txt`. PDF rendering uses WeasyPrint; the Dockerfile installs `libcairo2`, `libpango-1.0-0`, `libpangoft2-1.0-0` and the renderer is configured with a `no_network_url_fetcher` that refuses every non-`data:` URL at render time.

**GitHub Living System of Record (Phase 21)**: The one-shot Phase-13 export becomes a bidirectional, worker-driven system. All GitHub I/O runs on a durable **arq worker** — a real second process, not just a compose service: `worker: arq worker.WorkerSettings` in the `Procfile` (Railway), the `worker` service in `docker-compose.yml` (shares the backend image + Redis), and `worker.py` registers `export_push`, `reconcile_event`, `backfill_repo`, `increment_push`, `projects_sync`, `pr_check`, plus the periodic `reconcile_drift` cron. Jobs are idempotent and checkpointed (inbound keyed by `X-GitHub-Delivery`, outbound by `push_id`/`increment_id`), with bounded retries → backoff → dead-letter. The API process only **enqueues**: `POST /workspaces/{id}/export/github` returns **202** and never blocks on GitHub. Inbound events arrive at `POST /integrations/github/webhook` (HMAC-verified before any DB/queue work, against a two-secret rotation list, CSRF- and rate-limit-exempt); closing a task's issue (or merging its PR) flips that task to **done** inside SpecForge. Sync/drift state is `GET /workspaces/{id}/sync`; recovery is `POST .../sync/resync` and `POST .../sync/backfill` (both 202). The workspace evolves as a timeline of **increments** (`GET|POST /workspaces/{id}/increments`, `GET|POST /workspaces/{id}/ideas`). Identity is the SpecForge **GitHub App** (App JWT → Redis-cached per-installation tokens, never logged, private key in the secret manager). **The install callback is identity-verified (audit #1):** `GET /integrations/github/setup` never binds an installation to the caller on the `state` alone (the `installation_id` is attacker-controllable); it completes the App **user-to-server OAuth** (single-hop when the App's "Request user authorization (OAuth) during installation" is enabled and `code` arrives with the redirect, else a second authorize hop) and binds **only** after `GET /user/installations` confirms the caller participates in (can access) the installation — otherwise it refuses and audits `github.install.rejected`. (This is an access check, which is what closes the cross-tenant IDOR; it is not a strict org-ownership check.) This requires `GITHUB_APP_CLIENT_ID`/`_SECRET` (now mandatory when the App is enabled — enforced by `validate_production_settings`) and the App's **Callback URL = the setup endpoint**. **Issue↔task identity is the stable, content-derived `compute_task_ref(title)` (audit #2),** never the volatile human `T-NNN`: export, increment sync, the PR-body `Closes #N` map, and the Projects board all join on it, so re-finalising Tasks with a renumber/reorder updates each task's *same* issue instead of duplicating/closing it. Legacy rows persisted under `T-NNN` are migrated in place from the live GitHub issue titles on the next sync (`services/integrations/task_ref_migration.py`, fast-path-skipped once stable). **Push status is one canonical vocabulary** `pending`/`completed`/`failed`/`stale` everywhere (audit #4) — the retired legacy `in_progress`/`success`/`error` words are gone (migration `0028` normalises old rows), so a completed export serialises through `IntegrationPushRead` and `find_live_push`/`reconcile_drift` never misread it; a transient queue outage during **resync** restores the push's prior live status rather than failing a healthy push (audit #3). See `docs/RUNBOOK.md` §12 for App/webhook-secret rotation, installation-token re-mint, dead-letter replay, "sync paused" recovery, backfill, and increment-push ops. Phase 13's OAuth path is retained unedited behind a `provider` flag.

**Billing — Lemon Squeezy migration (Phase 22)**: Lemon Squeezy is the runtime payment provider (it supersedes the Phase-18 Stripe path; Lemon is the Merchant of Record, so it absorbs tax/chargebacks/disputes). The data model is **provider-neutral** (`billing_checkout_attempts`, `billing_credit_packs`, `billing_credit_debts`, `billing_admin_corrections`, `billing_webhook_events`, `billing_reconciliation_cursors`; the Stripe tables/rows are retained as audit history). Checkout is **attempt-first**: `POST /billing/checkout` commits an attempt row (snapshotting credits/price/currency/validity) *before* calling Lemon and returns a `checkout_ref` the frontend polls via `GET /billing/status?checkout_ref=…`. `POST /billing/webhook` verifies the `X-Signature` HMAC (two-secret list, fail-closed, CSRF/rate-limit-exempt) **before** any DB/queue work, commits the event to the durable `billing_webhook_events` inbox (deduped on the Lemon event id), then enqueues `billing_process_webhook` on the **same arq worker** — the HTTP path never grants inline. Grants are idempotent on `(provider, provider_order_id)` + the `billing_purchase:lemonsqueezy:{order}` ledger reason; `order_refunded`/fraud revokes via `apply_refund_reversal` (idempotent on `refund:billing:{pack}:{cents}`), and over-spent value becomes **recoverable billing debt** (expired value is never debt). Two crons keep it honest: a 60s pending-sweep and a 15-minute three-lane `billing_reconcile` (inbox replay / bounded `get_order` re-read / attempt hygiene) that **never auto-grants**. Failed jobs dead-letter to `billing:deadletter` (separate from `gh:deadletter`). The exceptional manual grant is `POST /billing/admin/correction` (allowlisted by `ADMIN_USER_EMAILS`, evidence-backed, idempotent, audited). The Stripe runtime is **fully decommissioned** (T-308): no SDK, no `STRIPE_*` config, no webhook processing — `POST /billing/webhook` answers a Stripe-shaped request (`Stripe-Signature` header) with `{"status":"ignored_provider_disabled"}` and no DB write; only the read-only `stripe_credit_packs`/`stripe_webhook_events` audit tables remain. **Payments are flag-gated with a second provider (issue #44):** `PAYMENTS_ENABLED` is the master kill switch (default **false**) and `PAYMENT_PROVIDER` picks **one** active gateway (`lemonsqueezy` | `razorpay`) — checkout is live only when `billing_checkout_enabled` = `payments_enabled and (active provider configured)`, surfaced to the frontend as the `enabled`/`provider` fields on `GET /billing/package` (which gates the Buy button). **Razorpay** is the INR alternative via hosted **Payment Links** (no SDK/CSP change; `services/razorpay_service.py` — `create_payment_link`/`get_payment`), grant authority `payment_link.paid` + reversal `refund.processed` at `POST /billing/webhook/razorpay` (`X-Razorpay-Signature` HMAC two-secret rotation, `provider_order_id`=the `pay_…` payment id); it is **not** a Merchant of Record (tax/dispute liability sits with the account holder, and reconcile lane 2 cannot detect a Razorpay chargeback — settle via admin-correction). The provider-neutral data model, attempt-first flow, inbox, `billing_process_webhook` job, `billing:deadletter`, and admin-correction are all shared; **both providers' webhooks always process regardless of the active flag (D3)** so a provider switch (flip `PAYMENT_PROVIDER`, restart) leaves old-order refunds/disputes settling, and `billing_reconcile` now claims **every configured provider's** cursor row upfront (`ORDER BY provider FOR UPDATE NOWAIT`, D11). See `docs/RAZORPAY_INTEGRATION_PLAN.md` and `docs/RUNBOOK.md` §9 (§9.9 for Razorpay ops) for billing alerts, rotation, dead-letter replay, reconcile, admin-correction, provider-switch, and account-deletion settlement ops.

## Environment Variables

Backend uses `.env` (see `backend/config.py` for all keys):
- `DATABASE_URL`, `REDIS_URL`
- `JWT_PRIVATE_KEY`, `JWT_PUBLIC_KEY` (RS256 PEM keys)
- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`
- `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_API_KEY`
- `ENCRYPTION_MASTER_KEY` (Fernet, for stored user API keys and GitHub OAuth tokens)
- `CSRF_SECRET`, `METRICS_TOKEN`
- Optional (Scalability audit P0 — all default-sane, each disable-able with `0`; see `.env.example` + `docs/RUNBOOK.md` §14): pool guards `DB_POOL_TIMEOUT` (5s)/`DB_STATEMENT_TIMEOUT_MS`/`DB_IDLE_IN_TRANSACTION_TIMEOUT_MS` and `REDIS_MAX_CONNECTIONS`/`REDIS_SOCKET_TIMEOUT`/`REDIS_SOCKET_CONNECT_TIMEOUT`/`REDIS_HEALTH_CHECK_INTERVAL`; admission `MAX_CONCURRENT_GENERATIONS_PER_PROCESS`/`_PER_USER`, `GENERATION_ADMISSION_LEASE_TTL_SECONDS`, `GENERATION_RATE_PER_MINUTE`/`_WINDOW_SECONDS`; provider budget/backoff `PROVIDER_MAX_INFLIGHT_GENERATIONS`/`PROVIDER_MAX_GENERATIONS_PER_MINUTE` (**ship at 0/unlimited — measure the per-org limit first**), `PROVIDER_RATE_LIMIT_MAX_RETRIES`/`_BACKOFF_BASE_SECONDS`/`_BACKOFF_MAX_SECONDS`.
- Optional: `SENTRY_DSN`, `GRAFANA_OTLP_ENDPOINT`, `GRAFANA_OTLP_TOKEN`
- Optional: `LANGFUSE_SECRET_KEY`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_HOST`
- Optional (Phase 22 Lemon Squeezy billing — the runtime payment provider): `LEMONSQUEEZY_API_KEY`, `LEMONSQUEEZY_STORE_ID`, `LEMONSQUEEZY_VARIANT_ID` (all three set ⇒ `lemonsqueezy_enabled`; checkout is disabled and `POST /billing/checkout` returns 503 when any is blank), `LEMONSQUEEZY_WEBHOOK_SECRET` + `LEMONSQUEEZY_WEBHOOK_SECRET_PREV` (HMAC `X-Signature` secrets; both accepted during a rotation window), `LEMONSQUEEZY_PRICE_CENTS`/`_CURRENCY`/`_CREDITS_PER_PURCHASE`/`_CREDIT_VALIDITY_DAYS`, `LEMONSQUEEZY_SUCCESS_URL` (HTTPS in prod; there is no cancel URL), and `LEMONSQUEEZY_TEST_MODE` (**must be `false`** in prod). When enabled in production, `validate_production_settings()` requires the webhook secret, an HTTPS success URL, positive price/credits/validity, and test mode off. `ADMIN_USER_EMAILS` is the comma-separated allowlist for `POST /billing/admin/correction`. The Phase-18 `STRIPE_*` settings and the Stripe SDK were removed by the T-308 decommission; only the read-only Stripe audit tables remain. Checkout is Lemon-only.
- Optional: `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` — GitHub OAuth App credentials. Leave blank to disable the GitHub export integration (Phase 13).
- Optional (Phase 21 GitHub App — the living integration): `GITHUB_APP_ID` (numeric App id, the JWT `iss`), `GITHUB_APP_SLUG` (public slug for the install URL), `GITHUB_APP_PRIVATE_KEY` (RS256 PEM that signs the App JWT — a secret-manager value, **never** stored in the DB), `GITHUB_APP_WEBHOOK_SECRET` and `GITHUB_APP_WEBHOOK_SECRET_PREV` (HMAC signing secrets; both accepted during a rotation window), and the identity-OAuth pair `GITHUB_APP_CLIENT_ID`/`GITHUB_APP_CLIENT_SECRET` (the App's user-to-server credentials; `github_app_identity_enabled` is true when both are set). The App is "enabled" when `GITHUB_APP_ID` + `GITHUB_APP_SLUG` are set; **in production, when enabled, `validate_production_settings()` requires `GITHUB_APP_PRIVATE_KEY`, `GITHUB_APP_WEBHOOK_SECRET`, and `GITHUB_APP_CLIENT_ID`/`GITHUB_APP_CLIENT_SECRET`** (an empty private key or missing identity OAuth fails startup). The identity OAuth is mandatory because the install callback verifies the installer can access (participates in) the installation before binding it (audit #1); the App's **Callback URL must point at `/integrations/github/setup`**, and enabling "Request user authorization (OAuth) during installation" makes that a single-hop verify. Leave all blank to keep the App off and fall back to the Phase-13 OAuth path.

## CI

`.github/workflows/ci.yml` runs on every push:
1. TruffleHog secret scan
2. Backend: ruff → black → bandit → pip-audit → pytest (80% coverage)
3. Frontend: pnpm audit → tsc → vitest → vite build
4. On `main` push: deploy backend to Railway, frontend to Vercel
